# API contract (Block 19)

Единый контракт backend API: формат ошибок, пагинация, OpenAPI, версионирование.
Frontend не должен угадывать форму ответа — все перечисленные структуры
описаны в `/v3/api-docs` и покрыты тестами.

## 1. Единый формат ошибок

Любой неуспешный ответ — `application/json` с телом `ErrorResponse`:

```json
{
  "timestamp": "2026-11-08T12:34:56Z",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "message": "Проверьте правильность заполнения полей",
  "traceId": "3f6c1f0e1b7a4f7e9a8c2d5b6e7f8091",
  "fieldErrors": [
    { "field": "email", "message": "Некорректный адрес электронной почты", "code": "Email" }
  ],
  "path": "/api/auth/register"
}
```

Обязательные поля контракта:

| Поле | Смысл |
| --- | --- |
| `status` | HTTP-код, дублирует статус ответа. |
| `code` | Стабильный машиночитаемый код (`ErrorType`). По нему можно ветвиться, не разбирая текст. |
| `message` | Безопасное человекочитаемое объяснение. Никогда не содержит SQL, имена классов и stack trace. |
| `traceId` | Идентификатор запроса. Совпадает с заголовком `X-Request-Id`. |
| `fieldErrors` | Список ошибок полей; пустой массив для не-валидационных ошибок. |

`timestamp` и `path` — диагностические поля, клиент не должен на них
полагаться. `fieldErrors` — именно список, потому что на одно поле может быть
несколько независимых нарушений; UI берёт первое сообщение на поле.

### Коды ошибок

| HTTP | `code` | Когда |
| --- | --- | --- |
| 400 | `BAD_REQUEST` | Некорректный запрос, параметр или тело. |
| 400 | `VALIDATION_FAILED` | Bean Validation / binding; заполнен `fieldErrors`. |
| 401 | `UNAUTHORIZED` | Нет токена, токен истёк или невалиден. |
| 403 | `FORBIDDEN` | Нет прав на операцию. |
| 403 | `ACCOUNT_BLOCKED` | Аккаунт заблокирован администратором. |
| 404 | `NOT_FOUND` | Ресурс не найден. |
| 409 | `CONFLICT` | Конфликт состояния или уникальности. |
| 413 | `PAYLOAD_TOO_LARGE` | Файл больше допустимого размера. |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Неподдерживаемый `Content-Type`. |
| 405 | `METHOD_NOT_ALLOWED` | Метод не поддерживается для ресурса. |
| 429 | `TOO_MANY_REQUESTS` | Сработал rate limit; есть `Retry-After`. |
| 500 | `INTERNAL_SERVER_ERROR` | Непредвиденная ошибка; детали только в логах. |

Коды из `ErrorType` — часть публичного контракта. Существующий код нельзя
переименовывать; для нового поведения добавляется новый код.

### Одинаковый конверт на всех уровнях

`@RestControllerAdvice` (`GlobalExceptionHandler`) и servlet-фильтры
(`JwtAuthFilter`, `RateLimiterFilter`, `SecurityConfig`) используют один и тот
же `ApiErrorWriter`, поэтому 401/403/429 от фильтров выглядят так же, как
ошибки контроллеров. Внутренние сообщения исключений остаются в логах и
связываются с ответом через `traceId`.

### Трассировка

`TraceIdFilter`:

- принимает входящий `X-Request-Id`, если он состоит из безопасных символов
  (`A-Za-z0-9._:-`, до 100 символов), иначе генерирует новый;
- кладёт значение в MDC (`requestId`) и в атрибут запроса;
- возвращает его в заголовке `X-Request-Id` любого ответа.

Пользователь может назвать `traceId` поддержке, и по нему находится запись в
логах.

## 2. Пагинация

Все крупные коллекции возвращают `PageResponse<T>`:

```json
{
  "content": [],
  "number": 0,
  "size": 20,
  "totalElements": 0,
  "totalPages": 0,
  "hasNext": false,
  "numberOfElements": 0,
  "first": true,
  "last": true,
  "empty": true
}
```

Канонические поля — `content/number/size/totalElements/totalPages/hasNext`.
Остальные сохранены для совместимости со Spring-клиентами.

Правила запроса:

- параметры `page` (0-based) и `size`; отрицательный `page` и `size < 1`
  отклоняются с 400;
- `size` ограничивается сервером (`PaginationConfig.maxPageSize`, по умолчанию
  100) — клиент не может запросить неограниченную страницу;
- сортировка задаётся только через whitelist сервера; неизвестное поле
  заменяется безопасным значением по умолчанию, а не приводит к 500;
- глубокие страницы стабилизируются tiebreaker по `id`, где это применимо.

Исключения:

- `/api/chats/{chatId}/messages/cursor` — cursor-пагинация
  (`items/nextCursor/hasMore`) для бесконечной прокрутки;
- `/api/posts/{postId}/comments` — собственный `CommentPageResponse`, потому
  что он агрегирует дерево комментариев; его поля документированы в OpenAPI;
- небольшие ограниченные коллекции (например, `/api/chats`,
  `/api/users/me/blocked`) возвращают массив без конверта.

## 3. OpenAPI

- Документ: `GET /v3/api-docs` (JSON), `GET /v3/api-docs.yaml` (YAML).
- UI: `/swagger-ui/index.html`.
- Версия springdoc — **3.x** (линия для Spring Boot 4 / Spring Framework 7).
  springdoc 2.x компилируется, но `/v3/api-docs` падает с 500
  (`NoSuchMethodError: ControllerAdviceBean.<init>(Object)`), поэтому версию
  нельзя понижать без понижения Boot.
- Оба пути публичны; авторизация описана схемой `bearerAuth`
  (`Authorization: Bearer <accessToken>`).
- Глобальные ответы 400/401/403/404/409/429/500 добавляются ко всем операциям;
  endpoint может переопределить их (например, 413/415 у загрузки изображений).
- `ErrorResponse` и `FieldErrorDto` регистрируются в `components`, потому что
  их возвращает advice, а не контроллер.
- Теги: Auth, Users & Blocks, Posts, Helps & Graph, Reviews & Ratings, Chat,
  Reports, Notifications, Admin — Moderation, Admin — Users,
  Admin — Wallet & Audit, Account, Achievements, Activity, Comments, Media,
  Search & Stats, Internal.
- Публичные операции помечены `@SecurityRequirements`, чтобы Swagger не
  требовал токен там, где он не нужен.

### Генерация frontend-клиента

Контракт можно превратить в типы и клиент без ручного копирования:

```bash
# Только TypeScript-типы (рекомендуется для текущего frontend)
npx openapi-typescript http://localhost:8080/v3/api-docs -o src/api/generated/schema.d.ts

# Полный клиент
npx @openapitools/openapi-generator-cli generate \
  -i http://localhost:8080/v3/api-docs \
  -g typescript-axios \
  -o src/api/generated
```

Сгенерированные файлы стоит коммитить и обновлять при изменении контракта.
Ручные обёртки (`src/api/*.ts`) остаются тонкими и используют сгенерированные
типы, а `utils/apiErrors.ts` — единая точка чтения `ErrorResponse`.

## 4. Версионирование

- Публичный префикс — `/api` (версия 1). Текущая версия отдаётся в заголовке
  `X-API-Version` на всех `/api/**` ответах и в `info.version` OpenAPI.
- **Совместимые изменения** остаются в текущей версии: новые endpoint'ы, новые
  необязательные поля, новые коды ошибок, новые значения enum, если клиент
  обязан игнорировать неизвестные значения.
- **Ломающие изменения** (переименование/удаление поля, смена типа, новые
  обязательные параметры, изменение семантики кода) уходят в `/api/v2`.
  Старая версия продолжает работать в течение документированного окна
  деprecation (минимум один релизный цикл) и помечается `deprecated` в
  OpenAPI.
- Ошибки и пагинация версионируются вместе с endpoint'ом: нельзя менять
  `ErrorResponse` или `PageResponse` несовместимо в рамках одной версии.
- Удаление старой версии — только после миграции frontend и отдельного
  решения; в коде остаётся `@Deprecated` и ссылка на новый путь.

## 5. Авторизация и права

- Публичные: регистрация/вход/refresh, публичная лента заявок, публичные
  профили, поиск, статистика, граф в публичной проекции, Swagger.
- `Authorization: Bearer <accessToken>` — всё остальное.
- `/api/admin/**` требует `ROLE_ADMIN`; контроллеры дополнительно проверяют
  администратора и возвращают 403 с `FORBIDDEN`.
- Владельческие проверки выполняются на сервере; frontend не решает, можно ли
  читать/менять ресурс.
- Приватные проекции (например, граф с именами и деталями, история рейтинга,
  кошелёк) возвращаются только владельцу и администратору.

## 6. Идемпотентность и фильтры

- Создание жалобы поддерживает `Idempotency-Key`; повтор с тем же ключом не
  создаёт дубль.
- Повторное удаление/снятие блокировки/отметка уведомления прочитанным не
  является ошибкой.
- Списочные endpoint'ы принимают фильтры, перечисленные в OpenAPI; неизвестные
  значения enum отклоняются 400, неизвестные параметры игнорируются.
- Загрузка изображений: `multipart/form-data`, 413 при превышении размера,
  415 при неподдерживаемом типе; оба ответа — `ErrorResponse`.

## 7. Чек-лист для frontend

1. Любой не-2xx ответ читать через `getApiErrorInfo` (`status`, `code`,
   `message`, `traceId`, `fields`).
2. Поля формы брать из `fields` — это уже нормализованный
   `Record<string, string>` из `fieldErrors`.
3. Для списков использовать тип `PageResponse<T>` и `page/size`; не
   рассчитывать на бесконечный `size`.
4. Не показывать пользователю сырой `message` для 500 — показывать безопасный
   текст и, при наличии, `traceId`.
5. При breaking change переключаться на `/api/v2` вместе с обновлением
   сгенерированных типов.
