# Безопасность изображений (Block 11)

Документ фиксирует модель угроз, серверные проверки и принятые решения по
загрузке изображений в Silo. Он дополняет `docs/MIGRATIONS.md` (раздел V48).

## 1. Модель угроз

Загрузчик изображений — точка, где недоверенные байты попадают в объектное
хранилище и затем отдаются другим пользователям. Рассматриваются угрозы:

- поддельный `Content-Type`/расширение и загрузка произвольного файла;
- decompression bomb (маленький файл с огромным разрешением);
- исчерпание диска/квоты большим числом объектов;
- перезапись или удаление чужого объекта через подставленный URL;
- утечка метаданных (GPS/EXIF) вместе с публичным изображением;
- публичный bucket, позволяющий анонимную запись, удаление или листинг;
- обращение к `/api/images/**` без аутентификации;
- «осиротевшие» объекты, на которые больше нет ссылок.

## 2. Проверки при загрузке

1. **Magic bytes.** Формат определяется только по первым байтам:
   JPEG (`FF D8 FF`), PNG (сигнатура 8 байт), GIF (`GIF87a`/`GIF89a`).
   `Content-Type` и имя файла клиента игнорируются.
2. **WebP отклоняется.** Java ImageIO без внешнего плагина не декодирует WebP,
   а зависимость от плагина сделала бы поведение зависимым от образа
   развёртывания. Клиенты получают явную ошибку и список JPEG/PNG/GIF.
3. **Размеры читаются до полного decode.** `ImageReader.getWidth/getHeight`
   вызываются до `read(0)`, поэтому `max-width`, `max-height` и `max-pixels`
   ограничивают выделение памяти даже для бомбы.
4. **Декодирование обязательно.** Повреждённый файл с валидной сигнатурой
   отклоняется.
5. **Перекодирование.** JPEG и PNG декодируются и кодируются заново. Это
   проверяет payload и удаляет EXIF/ICC/XMP, включая GPS. PNG сохраняет
   прозрачность; JPEG накладывается на белый фон, чтобы alpha не стала чёрной.
6. **GIF сохраняется как есть.** Перекодирование уничтожило бы анимацию,
   поэтому GIF только валидируется: кадры, бюджет пикселей, декодирование
   первого кадра. EXIF в GIF отсутствует.
7. **Лимиты.** Индивидуальный размер, суммарный размер запроса, число файлов,
   разрешение, пиксели, кадры GIF — всё задаётся на сервере и не может быть
   ослаблено клиентом.

## 3. Владение и квоты

- Ключ объекта генерирует сервер (`UUID` + расширение). Клиент не может
  выбрать ключ, а значит не может перезаписать чужой объект.
- `image_objects` хранит владельца, ключ, URL, размер, размеры и SHA-256.
  Уникальность `object_key` — второй барьер против перезаписи.
- Загрузка регистрируется в отдельной транзакции под
  `SELECT ... FOR UPDATE` строки пользователя: параллельные загрузки не могут
  обойти квоту (`quota-bytes`, `quota-count`).
- Создание/обновление поста вызывает `claimForOwner`: каждый URL должен быть
  `ACTIVE` и принадлежать автору. Аватар нельзя выдать за изображение поста.
- Мультизагрузка атомарна с точки зрения клиента: при ошибке уже записанные
  объекты удаляются (компенсация), строка владения не коммитится.

## 4. Удаление

- DELETE `/api/images?url=...` доступен только владельцу или администратору.
- Объект в Silo адресуется по `object_key` из строки владения, а не по
  клиентскому URL.
- Сначала в одной транзакции отвязываются `users.avatar_url` и
  `post_images.image_url`, затем строка становится `DELETED` (tombstone).
- Удаление из Silo выполняется после commit. Если Silo недоступен, tombstone
  остаётся, и cleanup повторит попытку.
- Замена аватара освобождает старый объект только если на него больше не
  ссылается ни один пост.

## 5. Bucket policy и доступ к API

- Bucket публичен только на чтение: `s3:GetObject` для `bucket/*`.
  `s3:ListBucket`, анонимные `PutObject`/`DeleteObject` не выдаются.
- Запись и удаление выполняются только серверными credentials.
- `/api/images/**` больше не является публичным: `permitAll` удалён, а
  `JwtAuthFilter.isPublicPath` не исключает этот префикс. Загружать и удалять
  изображения может только аутентифицированный пользователь.
- Публичная отдача самих файлов идёт напрямую из Silo по URL и не требует JWT.

## 6. Очистка

`ImageCleanupService` запускается по cron и обрабатывает три источника
батчами с ограничением на батч и на прогон:

1. `DELETED`-строки — удалить объект, затем строку;
2. `ACTIVE`-строки старше TTL, на которые нет ссылок, — атомарно пометить
   `DELETED` условным `UPDATE`, затем удалить;
3. объекты в bucket без строки владения старше TTL — удалить.

Условие «нет ссылок» продублировано в `UPDATE`, поэтому пост, созданный
параллельно, не потеряет изображение. Объекты моложе `orphan-ttl-hours`
защищены: это окно между записью в Silo и коммитом строки владения.

## 7. Антивирусная проверка

Block 21 добавляет ClamAV INSTREAM как опциональный шаг после
`ImageProcessor` и до записи объекта в Silo. По умолчанию сканирование
выключено (`ANTIVIRUS_ENABLED=false`), потому что не у всех развёртываний есть
демон ClamAV.

Когда сканирование включено, оно **fail-closed**:

- файл передаётся в ClamAV частями (`zINSTREAM\0`, chunk-size 64 KiB) без имени
  и других пользовательских метаданных;
- ответ `stream: OK` пропускает файл;
- ответ `... FOUND` возвращает `400 BAD_REQUEST` с безопасным сообщением;
- недоступный демон, timeout, обрыв соединения или неожиданный ответ
  возвращают `503 SERVICE_UNAVAILABLE` (`ErrorType.SERVICE_UNAVAILABLE`), а не
  «пропускаем на всякий случай».

Сканер работает поверх уже валидированных и перекодированных байтов: JPEG/PNG
проверяются после decode+re-encode, GIF — после проверки кадров и бюджета
пикселей. Это не заменяет структурную валидацию, а дополняет её. Для
наблюдаемости `/actuator/health` содержит индикатор `antivirus`
(`UP`/`DOWN`; при выключенном сканере — `UP` с деталью `disabled`).

## 8. Вложения чата (Block 21)

- Сообщение может содержать до трёх изображений (`ImagePurpose.CHAT`,
  `CHAT_MAX_ATTACHMENTS`). Клиент передаёт только URL, полученные от
  `/api/images`; сервер вызывает `claimForOwner` и проверяет, что каждый объект
  `ACTIVE` и принадлежит отправителю.
- Вложения не являются отдельным хранилищем: это те же `image_objects`, что и
  аватары/посты, с общей квотой, проверкой magic bytes, перекодированием и
  (опционально) антивирусом.
- При удалении сообщения объект освобождается только когда на него больше нет
  живых сообщений. Retention-уборка помечает такие объекты `DELETED`, после
  чего обычный `ImageCleanupService` удаляет их из Silo.
- Если сообщение удалено по retention, его URL перестаёт отдаваться, потому что
  строка объекта становится tombstone. Публичный bucket сам по себе не
  отзывает уже выданный URL, поэтому критичные изображения не следует считать
  вечно секретными.

## 9. Presigned upload

Presigned direct upload **не используется**. Он позволил бы клиенту писать в
bucket в обход сервера, но тогда сервер не смог бы:

- проверить magic bytes и декодировать изображение;
- прочитать размеры до decode и применить лимиты;
- удалить EXIF и перекодировать;
- проверить квоту до записи объекта.

Если прямой upload понадобится для очень больших файлов, безопасный вариант —
двухфазная схема: presigned upload в карантинный префикс, затем серверное
чтение, валидация, перекодирование и перенос в публичный префикс с записью
`image_objects`. До реализации такой схемы используется только серверная
загрузка.

## 10. Конфигурация

| Переменная | Назначение |
| --- | --- |
| `UPLOAD_MAX_SIZE` | максимум байт на один файл |
| `UPLOAD_MAX_REQUEST_SIZE` | максимум байт на весь multipart-запрос |
| `UPLOAD_MAX_FILES` | максимум файлов в одной загрузке |
| `UPLOAD_MAX_WIDTH` / `UPLOAD_MAX_HEIGHT` | максимум сторон |
| `UPLOAD_MAX_PIXELS` | максимум пикселей |
| `UPLOAD_GIF_MAX_FRAMES` | максимум кадров GIF |
| `UPLOAD_GIF_MAX_TOTAL_PIXELS` | бюджет пикселей GIF |
| `UPLOAD_QUOTA_BYTES` / `UPLOAD_QUOTA_COUNT` | квота пользователя |
| `IMAGE_CLEANUP_ENABLED` | включить cleanup |
| `IMAGE_CLEANUP_ORPHAN_TTL_HOURS` | TTL для бесхозных объектов |
| `IMAGE_CLEANUP_BUCKET_SCAN_ENABLED` | сканировать bucket без строк владения |
| `CHAT_MAX_ATTACHMENTS` | максимум изображений на одно сообщение (3) |
| `ANTIVIRUS_ENABLED` | включить ClamAV INSTREAM (fail-closed) |
| `ANTIVIRUS_HOST` / `ANTIVIRUS_PORT` | адрес демона ClamAV (по умолчанию `localhost:3310`) |
| `ANTIVIRUS_CONNECT_TIMEOUT_MILLIS` / `ANTIVIRUS_READ_TIMEOUT_MILLIS` | таймауты сканирования |
| `ANTIVIRUS_CHUNK_SIZE` | размер чанка INSTREAM (64 KiB) |

## 11. Тесты

- `ImageProcessorTest` — реальные JPEG/PNG/GIF, поддельные сигнатуры, WebP,
  лимиты размеров/пикселей/кадров, удаление EXIF и PNG-метаданных,
  сохранение прозрачности и анимационного GIF.
- `ImageServiceTest` — поддельный MIME не проходит, лимиты, компенсация
  частичной загрузки, read-only bucket policy, удаление по ключу владельца,
  запрет чужого удаления, идемпотентность.
- `ImageObjectServiceTest` — квоты, владение, `claim`, tombstone, освобождение
  заменённого аватара.
- `ImageCleanupServiceTest` — батчи, TTL, ошибки Silo, метрики.
- `AntivirusScannerTest` — выключенный сканер, чистый/заражённый/неожиданный
  ответ ClamAV, fail-closed на недоступном демоне.
- `ChatServiceTest` — лимит вложений, `claimForOwner` с `CHAT`, редактирование
  в окне, retention-батч и освобождение вложений последнего живого сообщения.
