# Жалобы и модерация (Block 15)

Документ фиксирует продуктовые правила домена жалоб и модерации после V51/V52.
Он описывает, что считается нарушением, кто и как принимает решение, какие
данные видят пользователи и администраторы, и как сервер гарантирует
атомарность и идемпотентность.

Главный принцип: **жалоба сама по себе ничего не блокирует**. Создание жалобы
лишь добавляет запись в очередь. Видимость контента и санкции меняются только
явным действием администратора, и каждое действие попадает в аудит.

## 1. Роли и видимость

| Роль | Возможности |
| --- | --- |
| `USER` | Создать жалобу, читать свои жалобы и их видимую историю. |
| `ADMIN` | Всё выше плюс очередь, карточка жалобы, метаданные, назначение и решения. |

Отдельной роли `MODERATOR` в системе нет. Все административные endpoint-ы
требуют `ADMIN`; проверка выполняется и в контроллере, и в сервисе.

Правила раскрытия данных:

- автор жалобы видит только свои жалобы (`GET /api/reports/me`,
  `GET /api/reports/{id}`);
- обычный пользователь не видит `internal_note`, имена и ID акторов служебных
  событий и события типа `NOTE`;
- администратор видит автора жалобы, его email, внутреннюю заметку, полную
  историю и применённые действия;
- скрытый или удалённый объект не раскрывается при попытке пожаловаться:
  сервер отвечает `404`, как будто объекта нет. Исключение — профиль
  пользователя, который остаётся видимым.

## 2. Типы целей

| Тип | Можно создать жалобу | Примечание |
| --- | --- | --- |
| `USER` | Да | На любого активного пользователя, кроме себя. |
| `POST` | Да | Пост должен быть `ACTIVE` и не soft-deleted. |
| `COMMENT` | Да | Комментарий и его пост должны быть `ACTIVE` и не soft-deleted. |
| `REVIEW` | Да | Автор отзыва не может жаловаться на свой отзыв; получатель отзыва может. |
| `MESSAGE` | Да | Только участник чата; удалённое сообщение не раскрывается. |
| `HELP`, `CHAT` | Нет | Оставлены в БД для исторических записей. |
| `REPORT` | Нет | Служебная цель для действий над самой жалобой. |

## 3. Причины, статусы и приоритеты

Причины (`ReportReason`):

`SPAM`, `ABUSE`, `HARASSMENT`, `INAPPROPRIATE`, `FRAUD`, `IMPERSONATION`,
`OTHER`.

Статусы (`ReportStatus`):

| Статус | Значение | `resolved_at` |
| --- | --- | --- |
| `OPEN` | Новая жалоба в очереди. | `NULL` |
| `IN_REVIEW` | Назначена администратору. | `NULL` |
| `RESOLVED` | Нарушение подтверждено, решение применено. | Заполнен |
| `REJECTED` | Нарушение не подтверждено. | Заполнен |
| `DUPLICATE` | Жалоба связана с original-жалобой. | Заполнен |

Приоритеты (`ReportPriority`): `LOW`, `NORMAL`, `HIGH`, `URGENT`. Новые
жалобы создаются с `NORMAL`.

Закрытую жалобу нельзя назначить или решить повторно: такие запросы
возвращают `409 Conflict`. Метаданные (`priority`, `internalNote`) при этом
править можно. Переоткрытие не входит в Block 15, но тип события `REOPENED`
уже зарезервирован в модели.

## 4. Создание жалобы

`POST /api/reports`

```json
{
  "targetType": "COMMENT",
  "targetId": 42,
  "reason": "ABUSE",
  "description": "Оскорбления в ответе"
}
```

Правила:

- `targetType` и `targetId` обязательны; `targetId > 0`;
- описание необязательно, очищается от управляющих символов и ограничено
  2000 символами; пустое описание сохраняется как `NULL`;
- жалоба на собственный объект запрещена (`400`);
- одна открытая жалоба на пару (`reporter_id`, `target_type`, `target_id`)
  запрещена (`409`). Это гарантирует частичный уникальный индекс
  `uq_reports_open_reporter_target`; после закрытия жалобы объект можно
  пожаловаться снова;
- проверка существования, видимости и владения выполняется на сервере по
  актуальному состоянию объекта, а не по данным клиента;
- аккаунт с активной блокировкой входа (`users.blockedUntil`) не может создать
  жалобу;
- rate limit использует общий `RateLimiterFilter`: `POST /api/reports`
  относится к social write path и расходует лимит `app.rate-limit.create-limit`
  (по умолчанию 60 запросов в минуту на аккаунт/IP/маршрут);
- каждое создание пишет событие `CREATED` с типом цели, ID и причиной.

### Идемпотентность

Клиент может передать заголовок `Idempotency-Key`:

- допустимы буквы, цифры, `.`, `_`, `:` и `-`, длина 1–100 символов;
- ключ уникален в рамках автора (`uq_reports_reporter_idempotency`), поэтому
  два пользователя могут использовать одно и то же значение;
- повторный запрос с тем же ключом возвращает уже созданную жалобу и не
  создаёт вторую;
- без заголовка идемпотентность не применяется, защита от дублей всё равно
  работает через правило одной открытой жалобы.

## 5. Публичная история жалобы

`GET /api/reports/me` — список жалоб автора. Параметры: `status`,
`targetType`, `reason`, `page`, `size`.

`GET /api/reports/{id}` — карточка своей жалобы. Возвращает только жалобы, где
`reporter_id` совпадает с текущим пользователем; иначе `404`, чтобы не
раскрывать чужие жалобы. Событие `NOTE` и все `internal_note` скрыты.

`GET /api/reports/meta` — справочник для формы: доступные цели, причины,
статусы, приоритеты и максимальная длина описания.

## 6. Очередь администратора

`GET /api/admin/reports`

Параметры (все необязательны): `status`, `targetType`, `reason`, `priority`,
`assignedModeratorId`, `reporterId`, `from`, `to`, `q`, `page`, `size`.
`from`/`to` — ISO local date-time, границы включительно; `from > to` даёт
`400`. `q` ищет по описанию и автору жалобы на стороне сервера. `size`
ограничен `app.pagination.max-page-size` (100).

`GET /api/admin/reports/{id}` — карточка рассмотрения:

- `report` — административная проекция жалобы, включая `internalNote`,
  `reporterEmail`, `duplicateOfId`;
- `target` — снимок объекта: владелец, заголовок, содержимое,
  `moderationStatus`, флаг `deleted`; скрытые и удалённые объекты
  администратору показываются;
- `events` — вся история, включая служебные заметки;
- `actions` — все применённые санкции и решения.

`PATCH /api/admin/reports/{id}` меняет только метаданные: `priority` и
`internalNote` (до 4000 символов). Статус здесь изменить нельзя. Если
значение реально изменилось, пишется событие `NOTE`; повторное сохранение тех
же значений не создаёт событие.

`POST /api/admin/reports/{id}/assign` берёт жалобу в работу:

- без тела назначает текущего администратора;
- `{ "moderatorId": 5 }` назначает другого `ADMIN`;
- `OPEN`/`IN_REVIEW` → `IN_REVIEW`, событие `ASSIGNED`;
- повторное назначение того же администратора при `IN_REVIEW` — no-op;
- закрытую жалобу назначить нельзя (`409`).

## 7. Решения и санкции

`POST /api/admin/reports/{id}/actions`

```json
{
  "actionType": "HIDE_CONTENT",
  "reason": "Подтверждено оскорбление",
  "resolution": "Скрыть комментарий на 7 дней",
  "expiresAt": "2026-11-14T12:00:00"
}
```

`reason` обязателен (1–1000 символов). `resolution` необязателен (до 1000).
`expiresAt` должен быть в будущем и используется для временных санкций.

Соответствие действий и итогового статуса:

| Действие | Цель в `moderation_actions` | Итог жалобы | Событие |
| --- | --- | --- | --- |
| `DISMISS_REPORT` | `REPORT` | `REJECTED` | `RESOLVED` |
| `LINK_DUPLICATE` | `REPORT` | `DUPLICATE` | `LINKED_DUPLICATE` |
| `RESOLVE_REPORT` | `REPORT` | `RESOLVED` | `RESOLVED` |
| `ESCALATE` | `REPORT` | `RESOLVED` | `ESCALATED` |
| `OTHER` | `REPORT` | `RESOLVED` | `RESOLVED` |
| `WARN`, `MUTE`, `UNMUTE`, `BAN`, `UNBAN` | жалоба/объект | `RESOLVED` | `RESOLVED` |
| `HIDE_CONTENT`, `REMOVE_CONTENT`, `RESTORE_CONTENT` | объект | `RESOLVED` | `RESOLVED` |

Дополнительные правила:

- `LINK_DUPLICATE` требует `duplicateOfId`; original-жалоба должна
  существовать, не быть дубликатом и указывать на тот же объект;
- `UNMUTE`/`UNBAN` требуют активной модерационной блокировки, иначе `409`;
- нельзя применить санкцию к собственной учётной записи;
- `MUTE`/`BAN` создают запись в `user_blocks` с `source = 'MODERATION'`;
  `users.blockedUntil` и долговые поля не изменяются;
- `WARN` не меняет состояние, но сохраняется в аудите;
- контентные действия поддерживаются для `POST`, `COMMENT`, `REVIEW`;
  для `MESSAGE` и исторических целей доступны только решения уровня жалобы
  и санкции над аккаунтом.

Жалоба, действие и событие пишутся в одной транзакции. Ошибка на любом шаге
откатывает все три записи: нельзя получить закрытую жалобу без действия или
действие без истории. Строка жалобы блокируется `SELECT ... FOR UPDATE`, поэтому
два администратора не примут конфликтующие решения одновременно.

Legacy `POST /api/admin/reports/{id}/resolve` оставлен для старых клиентов и
делегирует в тот же pipeline: `DELETE_COMMENT` превращается в
`REMOVE_CONTENT`, остальные действия — в `DISMISS_REPORT`.

## 8. Видимость контента

`posts`, `comments` и `reviews` имеют независимые поля:

- `deleted` — мягкое удаление автором; поведение и tombstone-ответы не
  изменились;
- `moderation_status` — решение модератора: `ACTIVE`, `HIDDEN`, `REMOVED`.

Правила:

- публичные списки и карточки постов, комментариев и отзывов требуют
  `moderation_status = 'ACTIVE'`;
- детальная карточка поста скрывает `HIDDEN`/`REMOVED` от всех, кроме автора
  и `ADMIN`; owner/admin-операции продолжают работать;
- на скрытый комментарий нельзя ответить;
- `HIDDEN` — временное скрытие, `REMOVED` — удаление модерацией. Авторское
  `deleted` и модерационное `REMOVED` не смешиваются;
- удаление/скрытие комментария уменьшает `posts.comments_count`, восстановление
  увеличивает; авторское удаление обрабатывается прежним кодом;
- рейтинг получателя пересчитывается при изменении статуса отзыва; в рейтинге
  участвуют только `ACTIVE` отзывы;
- администратор видит модерированный контент в карточке жалобы, публичные API
  его не отдают.

## 9. Временные скрытия

`HIDE_CONTENT` с `expiresAt` создаёт временное скрытие. Планировщик
`ModerationExpiryScheduler` запускается по cron
`app.moderation.expiry-cron` (по умолчанию `0 5 * * * *`) и восстанавливает
объект, если:

- у объекта всё ещё `moderation_status = 'HIDDEN'`;
- истёкший `HIDE_CONTENT` — последнее действие по этому объекту.

Более позднее `REMOVE_CONTENT` никогда не отменяется старым истёкшим
скрытием. Восстановление комментария и отзыва также обновляет счётчик
комментариев и рейтинг.

## 10. Аудит и хранение

`report_events` — append-only история жалобы. Типы: `CREATED`, `ASSIGNED`,
`STATUS_CHANGED`, `NOTE`, `ESCALATED`, `RESOLVED`, `REOPENED`,
`LINKED_DUPLICATE`, `ACTION_APPLIED`. Событие хранит актора, переход статуса,
`internal_note` и JSONB-метаданные.

`moderation_actions` — append-only журнал решений и санкций. Хранит жалобу,
модератора, цель, тип действия, причину, `expires_at` и JSONB-метаданные
(например, предыдущий `moderation_status`, ID созданной блокировки).

`user_blocks` — единый журнал блокировок. Модерационные блокировки имеют
`source = 'MODERATION'`, `blocked_by_id` и `lifted_*`; частичный индекс
`idx_user_blocks_active_moderation` ускоряет проверку активной блокировки.

Жалобы, события и действия хранятся бессрочно для аудита. PII минимизируется:
при анонимизации аккаунта исторические ссылки сохраняются, но персональные
данные из `users` очищаются. Контент может быть удалён или скрыт, сама запись
жалобы остаётся.

## 11. Схема и проверка

V51 (аддитивная, с переименованиями):

- `reports.details → description`, `assigned_to_id → assigned_moderator_id`;
- новые `internal_note`, `duplicate_of_id`, `idempotency_key`;
- `REVIEW` в `chk_reports_target_type`; `REPORT` остаётся допустимым только
  для `moderation_actions`;
- новые типы событий и действий;
- `moderation_status` в `posts`, `comments`, `reviews` и partial-индексы
  публичных выдач;
- partial-индекс активных модерационных блокировок.

V52 добавляет `idx_posts_public_moderated_feed`: V51 пыталась расширить
`idx_posts_public_feed`, но этот индекс уже существовал с V46, и
`CREATE INDEX IF NOT EXISTS` молча оставил старую версию без
`moderation_status`. Применённые миграции не переписываются, поэтому
недостающий индекс добавлен отдельной миграцией под новым именем.

Проверка контракта:

```powershell
Get-Content scripts\fixtures\verify_block15_schema.sql -Raw |
  docker exec -i postgres psql -U helpTree -d helpTree_db -v ON_ERROR_STOP=1
```

Fixture проверяет колонки и их типы, переименования, CHECK-контракты, unique и
partial-индексы, FK `duplicate_of_id`, значения `moderation_status`, а также
инварианты данных: закрытая жалоба всегда имеет `resolved_at`, открытая — нет;
жалоба не может быть дубликатом самой себя.

## 12. Тесты

- `ReportServiceTest` — создание, идемпотентность, дубли, права, назначение,
  решения, метаданные и видимость истории;
- `ModerationServiceTest` — проверка целей, preview, контентные и аккаунтные
  действия, восстановление временных скрытий, счётчик комментариев;
- `PostSpecificationTest` — фильтрация `moderation_status`;
- `CommentThreadIntegrationTest` — полный цикл жалобы на комментарий,
  модерационное удаление и публичная выдача без tombstone;
- контроллерные тесты — авторизация и контракт ответов.
