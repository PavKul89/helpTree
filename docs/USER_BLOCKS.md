# Пользовательские блокировки (Block 16)

Документ описывает самостоятельный механизм пользовательских блокировок после
V53. Его главный принцип: **блокировка проверяется на сервере в каждом
утверждённом сценарии**, а не только скрывает кнопки на frontend.

Этот домен не связан с санкциями платформы:

- `users.blockedAt` / `users.blockedUntil` — блокировка входа или долговая
  блокировка аккаунта;
- `user_blocks` (V42) — журнал модерационных и долговых санкций;
- `user_blocks_relations` (V53) — персональная настройка пользователя
  «ограничить взаимодействие с этим человеком».

Block 16 не переиспользует и не переименовывает первые два механизма.

## 1. Области блокировки

| Scope | Что закрывает |
| --- | --- |
| `ALL` | Все сценарии ниже, включая комментарии. |
| `MESSAGES` | Создание чата и отправку сообщений. |
| `PROFILE` | Публичный профиль, директорию пользователей, поиск пользователей и отзывы. |
| `HELP_REQUESTS` | Отклик на чужую заявку о помощи (`acceptHelp`). |

`ALL` является надмножеством: строка со scope `ALL` срабатывает в любом
сценарии. Комментарии не имеют отдельного scope и закрываются только `ALL`.

Блокировка **двусторонняя внутри scope**. Если A заблокировал B в `MESSAGES`,
то ни A → B, ни B → A не могут создать чат или отправить сообщение. Строка при
этом хранится одна — направление `A → B`.

## 2. Модель данных

Таблица `user_blocks_relations`:

| Колонка | Тип | Правило |
| --- | --- | --- |
| `id` | `BIGSERIAL` | Primary key. |
| `blocker_id` | `BIGINT` | `FK → users(id) ON DELETE CASCADE`. |
| `blocked_id` | `BIGINT` | `FK → users(id) ON DELETE CASCADE`. |
| `scope` | `VARCHAR(20)` | `ALL`, `MESSAGES`, `PROFILE`, `HELP_REQUESTS`; default `ALL`. |
| `created_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP`. |
| `expires_at` | `TIMESTAMP NULL` | `NULL` = бессрочно; иначе должен быть позже `created_at`. |

Ограничения:

- `uq_user_blocks_relations_pair` — уникальность пары
  `(blocker_id, blocked_id)`, поэтому на пару существует не более одной строки;
- `chk_user_blocks_relations_self` — нельзя заблокировать самого себя;
- `chk_user_blocks_relations_period` — срок должен быть в будущем относительно
  `created_at`;
- `chk_user_blocks_relations_scope` — только утверждённые scope.

`expires_at` не удаляет строку и не требует планировщика: все запросы
сравнивают `expires_at` с текущим временем. Просроченная связь просто
перестаёт действовать. Повторный `POST` переиспользует её и обновляет
`scope`/`expires_at`.

## 3. API

Все endpoint-ы требуют авторизации. Ответы с ошибками используют общий
контракт приложения: `401` — нет сессии, `403` — действие запрещено, `404` —
пользователь не найден, `400` — неверный запрос.

### 3.1. Заблокировать или обновить блокировку

`POST /api/users/{id}/block`

Тело необязательно:

```json
{
  "scope": "MESSAGES",
  "expiresAt": "2026-12-31T23:59:59"
}
```

- пустое тело — бессрочная блокировка `ALL`;
- `scope` по умолчанию `ALL`;
- `expiresAt: null` или отсутствие поля — бессрочно;
- `expiresAt` в прошлом или настоящем — `400`;
- `id` равен текущему пользователю — `400`;
- несуществующий или удалённый пользователь — `404`;
- повторный вызов не создаёт вторую строку, а обновляет существующую пару
  (атомарный `INSERT ... ON CONFLICT DO UPDATE`).

Ответ `200`:

```json
{
  "id": 12,
  "blockerId": 1,
  "blockedId": 2,
  "scope": "MESSAGES",
  "createdAt": "2026-11-07T12:00:00",
  "expiresAt": "2026-12-31T23:59:59",
  "active": true
}
```

### 3.2. Разблокировать

`DELETE /api/users/{id}/block`

- удаляет связь текущего пользователя с `{id}`;
- идемпотентен: если связи нет, всё равно `204 No Content`;
- несуществующий пользователь — `404`;
- удалить можно только собственную блокировку; направление «меня заблокировали»
  снимает только автор блокировки.

### 3.3. Список своих блокировок

`GET /api/users/me/blocked`

Возвращает только активные (не просроченные) строки, созданные текущим
пользователем:

```json
[
  {
    "id": 12,
    "userId": 2,
    "name": "Bob",
    "avatarUrl": null,
    "scope": "ALL",
    "createdAt": "2026-11-07T12:00:00",
    "expiresAt": null
  }
]
```

### 3.4. Статус для пары

`GET /api/users/{id}/block-status`

```json
{
  "userId": 2,
  "blockedByMe": true,
  "blockedMe": false,
  "active": true,
  "scope": "ALL",
  "expiresAt": null
}
```

Поля независимы: пользователи могут заблокировать друг друга. `scope` и
`expiresAt` описывают собственную блокировку зрителя, если она есть, иначе
входящую. Для самого себя все флаги `false`.

## 4. Серверный enforcement

| Сценарий | Проверка | Scope |
| --- | --- | --- |
| Создание чата | `ChatService.createChat` | `MESSAGES` |
| Отправка сообщения | `ChatService.sendMessage` | `MESSAGES` |
| Отклик на заявку | `HelpService.acceptHelp` | `HELP_REQUESTS` |
| Создание комментария | `CommentService.createComment` | `ALL` |
| Создание отзыва | `ReviewService.createReview` | `PROFILE` |
| Публичный профиль | `UserController.getUserPublic` | `PROFILE` |
| Директория пользователей | `UserSpecification.excludeProfileBlocks` | `PROFILE` / `ALL` |
| Поиск пользователей и отзывов | `SearchRepository` (`NOT EXISTS`) | `PROFILE` / `ALL` |

Ключевые свойства:

- единая точка проверки — `UserBlockService.assertInteractionAllowed`;
- запрос ищет активную строку в обоих направлениях и допускает либо точный
  scope, либо `ALL`;
- фильтрация директории и поиска выполняется в SQL, поэтому пагинация и
  `totalElements` остаются корректными; фильтрация уже загруженной страницы
  дала бы неверный размер;
- анонимный поиск передаёт `viewerId = -1`, чтобы тип параметра native-запроса
  оставался стабильным;
- публичный профиль кэшируется, поэтому проверка `PROFILE` выполняется в
  контроллере до обращения к кэшу.

При срабатывании блокировки сервер отвечает `403 Forbidden` с понятным
сообщением. Frontend не является источником истины: прямой вызов API или
повторная отправка запроса всё равно проверяются на сервере.

## 5. Взаимодействие с другими механизмами

- Блокировка аккаунта (`blockedUntil`) и долг проверяются отдельно и раньше
  пользовательской блокировки; `403`/`400` могут вернуться по любой из причин.
- Модерационные санкции (`HIDDEN`/`REMOVED`, `user_blocks` V42) не заменяются
  пользовательской блокировкой и наоборот.
- Удаление пользователя каскадно удаляет его пользовательские блокировки.
- Жалобы и модерация не создают пользовательские блокировки автоматически:
  это разные домены.

## 6. Ограничения

- Нельзя заблокировать самого себя.
- Нельзя заблокировать несуществующего или удалённого пользователя.
- Нельзя задать срок в прошлом.
- Одна пара — одна строка; изменить направление можно только удалив свою
  блокировку и создав новую.
- Блокировка не скрывает исторические сообщения, отзывы или комментарии,
  созданные до неё; она запрещает новые взаимодействия в своём scope.
- `GET /api/users/me/blocked` показывает только собственные исходящие
  блокировки; входящие видны через `block-status`.

## 7. Frontend

На странице чужого профиля доступны:

- кнопка «Заблокировать» с выбором scope и подтверждением;
- кнопка «Разблокировать», если текущий пользователь уже заблокировал этого
  человека;
- предупреждение, если другая сторона ограничила взаимодействие.

На собственном профиле отображается список заблокированных с областью
блокировки и кнопкой снятия. Все действия вызывают API и обновляют состояние
по ответу сервера; UI не пытается самостоятельно вычислять enforcement.

## 8. Проверка

Unit-тесты:

- `UserBlockServiceTest` — self-block, отсутствующий пользователь, срок,
  upsert, идемпотентный delete, статус, expiry и маппинг scope;
- `ChatServiceTest` — `MESSAGES` для создания чата и сообщения;
- `CommentServiceTest` — `ALL` для комментария;
- `ReviewServiceTest` — `PROFILE` для отзыва;
- `HelpServiceTest` — `HELP_REQUESTS` для отклика;
- `UserControllerOwnershipTest` — сигнатуры публичной директории.

Интеграционный тест `UserBlockIntegrationTest` (запускается с
`INTEGRATION_TEST=true`) проверяет на реальной PostgreSQL:

- одну строку на пару и обновление scope/expiry;
- серверное истечение блокировки;
- двустороннюю блокировку чатов и сообщений;
- `HELP_REQUESTS` при отклике на заявку;
- скрытие пары из директории и native-поиска.

Схема дополнительно проверяется
`scripts/fixtures/verify_block16_schema.sql` и `flyway:validate`.
